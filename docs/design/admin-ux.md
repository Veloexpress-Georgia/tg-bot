# Админский интерфейс: экраны, состояние и навигация

Решение и план, 11 сентября 2026. Направление согласовано: админский UX строится
вокруг трёх задач — провести ближайший день, подготовить следующие заброски,
разобраться с прошлым и деньгами. Документ описывает целевую модель экранов,
принятые решения по реализации и отложенные идеи.

## 1. Что было до изменений

Одна карточка в личном чате админа. `/start` отправлял её заново, удаляя
предыдущую. Фоновое обновление (`_refresh_booking_monitors`) редактировало то же
сообщение текстом монитора после каждого голоса, оплаты, отмены и тика воркера.

Карта экранов и переходов до изменений:

| Экран | Callback | Кто рисует |
|---|---|---|
| Стартовая карточка | `/start` | `render_start_status` + `start_menu_keyboard` |
| Монитор дня | `mon:day:<date>` | `render_booking_monitor` |
| Все участники | `mon:all:<date>` | `render_all_riders` |
| Управление бронями | `mon:manage:<date>` | `render_booking_management` |
| Карточка заброски | `mon:managelift:<date>:<time>` | `render_lift_detail` |
| Ручные места | `mon:add/sub:<date>:<time>` | возвращает на управление бронями |
| Подтверждение отмены заброски | `mon:cancel:…` | `render_cancel_lift_confirmation` |
| Подтверждение отмены дня | `mon:cancelday:<date>` | `render_cancel_day_confirmation` |
| История | `mon:history[:<date>]` | `render_lift_history` |
| День истории | `mon:past:<date>` | `render_lift_day_audit` |
| Тренд по времени | `mon:trend` | `render_lift_trend` |
| Статистика | `stats:`/`astats:`/`rstats:` | `render_statistics` |
| Прошлые расчёты возврата | `mon:refunds` | отдельные сообщения |
| Weekend | `menu:weekend_plan`, `plan:*` | `render_plan_card` |
| Расписание публикации | `plan:schedule`, `sched:*` | `render_schedule_card` |
| Дополнительный день | `menu:extra_day`, `extra:*` | `render_extra_day_card` |
| Значения по умолчанию | `menu:service_defaults`, `defaults:*` | `render_service_day_defaults` |

Проблемы, которые решает этот документ:

1. **Фоновое обновление меняло назначение экрана.** Любой вложенный экран
   заменялся монитором при следующем голосе. Временное «открепление» монитора
   удаляло долговременную регистрацию админа и лишало его дальнейших
   автообновлений.
2. **Шапка монитора нечитаема**: `At minimum 2 of 2 · funded 0 · 16 seats ·
   claimed 3/9 · 60 of 240 GEL` — шесть чисел в строке.
3. **`11/10` читалось как «11 подтверждённых мест в десятиместной машине»**.
   Очередь не была отделена от занятых мест.
4. **`Needs attention` суммировал разные категории** (неоплата, наличные,
   очередь, поздние выходы), один человек попадал в несколько.
5. **`Cash to collect`** называл задолженностью деньги, которые райдер уже
   передал наличными и которые уже записаны в журнал как полученные.
6. **Лишний уровень `Manage bookings`** между днём и конкретной заброской.
7. **Переход «Дни» из статистики терял период**.
8. **Предпросмотр отмены** не существовал: единственный расчёт возврата
   одновременно сохранял `RefundReport`.

## 2. Согласованные требования

Из постановки задачи, менять только по согласованию:

- Три задачи админа задают структуру, а не внутренние модули бота.
- `/start` сразу показывает полезное состояние; при наличии активных дней —
  монитор ближайшего подходящего дня, сегодняшний в приоритете.
- Обычные переходы живут в одной управляемой карточке; «Назад» сохраняет
  контекст (день, период, страницу).
- Фоновые обновления не выбрасывают админа из открытого экрана.
- Админ не выполняет sync/repair-команды.
- Английский язык интерфейса сохраняется.
- Финансовая арифметика не меняется ради красивой сводки.
- Правила оплаты, возвратов, вместимости, минимума, прав доступа и публичности
  статистики не меняются.
- `RefundReport` — накопительный расчёт, не факт выплаты.

## 3. Целевая модель экранов

```
/start
 ├─ есть активные дни → 📊 Day (сегодня, иначе ближайший впереди)
 └─ нет активных дней → та же карточка рисуется как ☰ Menu

📊 Day
 ├─ [вкладки дней]            → тот же экран, другой день
 ├─ [8:30] [10:00] … (по 3)   → 🚲 Lift, прямо, включая ненабравшиеся
 ├─ 👥 All riders             → состав всего дня
 ├─ 🚫 Cancel day             → подтверждение → отмена → оставшиеся дни
 └─ ☰ Menu

🚲 Lift
 ├─ ➖/➕ Offline seat          → тот же экран
 ├─ 🚫 Cancel / ♻️ Restore     → подтверждение с расчётом → результат
 └─ ⬅️ Back                   → день, с которого пришли

☰ Menu
 ├─ 📋 Weekend · ➕ Extra day  → планирование
 ├─ 📜 History · 📈 Statistics → прошлое и деньги
 ├─ ⚙️ Settings · 🧾 Refunds   → цена, дедлайн, расписание, расчёты возврата
 └─ 📊 <день>                 → назад к текущему дню (если он есть)
```

Меню оставлено плоским: отдельный экран «Планирование» добавлял бы нажатие
перед самым частым действием недели, а четыре пункта из постановки задачи —
ориентир, а не обязательная квота. Расписание публикации живёт в настройках и
дублируется ссылкой на карточке Weekend, потому что это ответ на два разных
вопроса: «когда откроются опросы вообще» и «когда откроется вот этот weekend».

Принцип: «одна строка — один факт». Крупные вертикальные кнопки ограничены;
однотипные мелкие действия живут в одной строке.

## 4. Принятые решения по реализации

### 4.1. Навигационное состояние вместо открепления монитора

Строка `admin_booking_monitor` остаётся долговременной регистрацией админа как
получателя карточки. К ней добавлены два поля:

- `screen` — имя открытого экрана;
- `screen_state` — JSON с контекстом (`lift_time`, `period`, `page`, `rider_id`,
  `before`, `back`).

Экраны делятся на два класса:

- **живые** (`day`, `riders`, `lift`) — фоновое обновление перерисовывает именно
  их, с новыми данными и тем же контекстом;
- **замороженные** (все остальные: меню, планирование, настройки, история,
  статистика, подтверждения) — фоновое обновление их не трогает.

Регистрация не удаляется никогда: открытие настроек больше не лишает админа
утреннего монитора и автообновлений.

Разделение сущностей:

| Сущность | Где живёт |
|---|---|
| Регистрация админа | строка `admin_booking_monitor` |
| ID текущего сообщения | `telegram_message_id` той же строки |
| Открытый экран | `screen` |
| Выбранный день | `selected_service_date` |
| Период, страница, райдер, контекст возврата | `screen_state` |

Два админа независимы: строка одна на `admin_user_id`.

### 4.2. Читаемая сводка дня

Шапка разбита на короткие строки:

```
📊 Sat, 12 Sep
3 of 5 lifts running · 3 funded
Reported 360 of 450 GEL

🚐 10:00 · 10 seats · full · funded
🚐 11:45 · 10 seats · 1 waiting · funded
🚐 13:30 · 10 seats · full · funded
💤 Not filled: 8:30, 15:30

🔴 No payment reported: @anna, @nika
💵 Reported in cash: @vitaly
⏳ Waitlist: @giorgi 11:45 #1
```

Решения:

- Занятые места и очередь — разные числа. `11/10` больше не печатается: строка
  говорит «10 seats · 1 waiting».
- `claimed` → `reported`: бот знает только то, что райдер сообщил.
- `Cash to collect` → `Reported in cash`: деньги уже переданы, это не долг.
- Общий счётчик `Needs attention` убран: он складывал несравнимые категории и
  считал одного человека дважды.
- «Набралось» (`running`) и «обеспечено оплатой» (`funded`) остаются разными
  строками и никогда не сливаются в «точно едет».

### 4.3. Прямой доступ к заброске

Промежуточный экран `Manage bookings` убран. Времена дня — кнопки прямо в
мониторе; ненабравшиеся заброски тоже кликабельны. Карточка заброски содержит
состав, ручные места, состояние оплат, отмену/восстановление и возврат ровно на
тот день, с которого пришли.

`All riders` сохранён: это самостоятельная задача — прочитать состав всего дня
одним экраном.

### 4.4. Предпросмотр отмены без записи отчёта

`PaymentsService.cancellation_report` сохраняет `RefundReport` и остаётся
операцией после отмены. Для подтверждения добавлен read-only
`cancellation_preview`, который считает те же строки и ничего не пишет.

Оба используют один расчёт с флагом `pending`. Он нужен, потому что отчёт
вызывается после отмены, когда заброска уже ушла из бронирований райдера, а
предпросмотр — до неё, когда она ещё там. Без поправки каждый предпросмотр
сообщал «нечего возвращать».

### 4.5. Период не теряется

Переходы истории и статистики несут период и страницу в callback-данных и в
`screen_state`. Формат — `mon:history[:<курсор>[:<период>]]` и
`mon:past:<дата>[:<период>]`, где курсор это `0` для свежей страницы. «Дни» из
статистики открывает историю с тем же периодом, «Назад» возвращает на ту же
страницу списка. Период в callback-данных, а не только в состоянии: так кнопка
на старой карточке ведёт туда же, куда вела при отрисовке.

### 4.6. Ширина строки вместо количества имён

Категории («без отметки оплаты», «в очереди») показывали до восьми имён. Восемь
обычных ников в строку помещаются, три длинных — нет, и строка превращалась в
абзац. Бюджет теперь в символах, с учётом длины подписи слева.

### 4.7. Список забросок возвращает сервис

Гостевое «на все заброски» читало времена обратно из отрендеренной клавиатуры
карточки. Видимость кнопки определяла денежную операцию. Правило переехало в
`PaymentsService.guest_lift_times`; разметка снова только показывает.

### 4.8. Планирование говорит, что именно изменится

На карточке Weekend появилась строка о том, что правки сохраняются как план и
до назначенного времени или `🚀 Post now` в группу ничего не уходит.
Предупреждение перед `♻️ Recreate polls` называет конкретные дни и то, что
райдеры потеряют ответы, вместо общей фразы «опросы уже опубликованы».
`⏭ Skip weekend` остался только на карточке weekend: на карточке расписания это
была вторая кнопка для одного флага, называющая weekend иначе.

Результат публикации заменяет карточку планирования и предлагает открыть
созданный день. Раньше он жил три секунды в toast, а на экране оставался план,
всё ещё выглядящий как невыполненная работа.

## 5. Отложенные идеи

- Ввод точной цены числом вместо шагов `±1 GEL`.
- Фильтр «только своевременно записанные дни» в статистике.
- Сортировка списка райдеров по последнему участию.
- Отметка админом факта получения наличных (`verified_by_user_id` сейчас
  только читается).
- Разделение `PaymentsService` на денежные операции и управление сообщениями —
  отдельная задача из обзора от 10 сентября.

## 6. Чего не делаем

Редактирование шаблонов, сайт, miniapp, штрафы, междневные балансы, рейтинги
надёжности, no-show и прибыль — вне области. Данных для последних трёх в учёте
нет.
